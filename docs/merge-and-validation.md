# Mac 合并与功能验证

更新日期：2026-09-09。主项目为 `medical-platform/Medical`（前端）与 `backend`。运行方式见根目录 README。

## 合并处理

顶层 Mac 副本包含旧版 `Medical/Medical/src` 和新版 `Medical/Medical/V1/src`，以及依赖缓存、构建输出和 `__MACOSX` 元数据。检查过的源文件可正常按 UTF-8 解码，没有发现 NUL 或无效 UTF-8；没有据此认定某个具体源码文件被损坏。Mac 依赖包含 Darwin ARM64 专用 Rollup 项，不能直接覆盖 Windows 的依赖配置。

采用功能合并：保留主项目真实 JWT 登录、患者授权、数据库病历、影像上传与模型接口；合入 V1 的语言字典、通用组件、本地 DICOM 解码初始化、模态识别和配套测试。Vite 保留主项目 API 代理，接入解码器依赖和 ES worker 配置。患者表格、报告卡片、时间线等按真实 API 类型适配。

Mac 的本地 mock 登录、仅 localStorage 保存的病历、审核状态和旧几何占位图没有覆盖主项目数据流程。对应需求改成后端持久化的患者管理、个人资料、影像确认及多器官关联。Cornerstone 组件和 DICOM 模态工具保留为兼容源代码；当前线上影像入口仍接收 NIfTI，未把 DICOM 或压缩包解析测试当作生产 DICOM 导入支持。

删除顶层 Mac 目录前，在忽略 Git 的 `.cache/mac-source-before-merge.zip` 留存源代码、配置和测试资料，并验证压缩包可读。大体积安装缓存与 Mac 元数据不进入主项目；顶层 `Medical` 清理后不影响 `medical-platform/Medical`。

`0002` 增加个人资料、文件、患者归档及确认表；`0003` 增加病历与器官关联表，并回填原主器官。旧 `organ_id` 字段和调用方式保留，多器官列表用 `organ_ids`。没有重复复制病历正文。

## 解压与切片性能

公开样本下载后先完整保存本地并校验，再解压转换。上传完成前将原始 NIfTI 验证、转换为 canonical RAS 的 float32 `.slices.npy`，通过临时文件原子替换。后续每个视图用只读内存映射取所需平面。256 MiB 的引用缓存限制不会让所有上传影像常驻 Python 内存；操作系统按访问页面调入数据。

这项优化消除了浏览时的重复整卷解压，也能跨进程重启保留缓存。原始影像保留用于推理。缓存磁盘成本约为体素数乘 4 字节；旧影像首次访问会准备一次缓存，截断缓存会重建。解码维度、体素数和内存上限仍受配置约束，缓存命中不跳过鉴权。

服务端按需切片的像素与请求计时保存在 `.cache/real-imaging/validation/results.json`。即便消除重复解压，逐张请求仍包含网络和 PNG 解码时间，所以进一步加入下述浏览器本地连续渲染。

### 连续浏览改进

服务端缓存只解决解压，旧前端仍有每层 100 ms 防抖、请求及 PNG 解码等待。因此增加带权限的 `/medical-images/{id}/volume` 接口，流式传输已准备好的 NPY 文件。浏览器先显示初始预览，同时完整加载体积并转移给独立 Web Worker；无需在主线程复制第二份体积。Worker 同时支持 NPY 的 C-order 和 Fortran-order，按存储步长安排读取顺序。

就绪后由本地 Worker 计算窗宽与三方向像素，Canvas 绘制。方向键和拖动事件合并到下一动画帧，每个方向只保留最新待绘目标，最多一个绘制任务正在执行；旧帧在新帧完成前保持显示，层号对应实际画面。窗宽切换不重新下载体积。每卷当前限制为 256 MiB float32 数据，超过限制时明确使用逐张预览。

体积不写入 localStorage、IndexedDB 或浏览器磁盘缓存。切换检查、退出页面和退出登录会终止 Worker 并释放引用；当前页每 30 秒复核权限，归档或撤销访问返回 401/403/404 后清空显示。整卷已下载的数据不能像尚未传输的数据一样即时收回，因此未宣称每次本地切层都向服务端鉴权。

验证脚本使用真实体积连续绘制 180 个跨方向位置：最终一次本机测量中 CT 中位 0.95 ms、P95 6.05 ms、最大 6.93 ms；MRI 中位 2.19 ms、P95 3.89 ms。该基准是同一渲染函数在 Node/V8 下的计算耗时，不含屏幕刷新、Worker 消息传递或首次下载，也不是生产并发保证。输出为 `.cache/real-imaging/validation/browser-renderer-benchmark.json`。浏览器另外验证了本地模式、连续方向键、Home/End、实际滑块拖动和窗宽切换，层号与画面一致。

```powershell
# 先运行上文的真实影像验证，生成受保护体积及参考像素
cd medical-platform/Medical
pnpm test:volume --real
```

## 真实影像来源与检查

样本来自 [3D Slicer 官方 SampleData 注册表](https://github.com/Slicer/Slicer/blob/main/Modules/Scripted/SampleData/SampleData.py) 与 [SlicerTestingData 发布仓库](https://github.com/Slicer/SlicerTestingData)。下载地址由官方校验标识固定。脚本先校验 SHA-256，再转换已知的标量 gzip NRRD，保留空间方向、原点和间距；这不是通用 NRRD 转换器。

| 样本 | canonical 体素矩阵 | 间距 mm | SHA-256 |
| --- | --- | --- | --- |
| CT-chest | 512 × 512 × 139 | 0.761719 × 0.761719 × 2.5 | `4507b664690840abb6cb9af2d919377ffc4ef75b167cb6fd0f747befdb12e38e` |
| MR-head | 130 × 256 × 256 | 1.299995 × 1 × 1 | `cc211f0dfd9a05ca3841ce1141b292898b2dd2d3f08286affadf823a7e58df93` |

验证脚本使用临时数据库和独立文件目录，走真实登录、患者录入、影像上传和切片 API。对每份样本的三个方向分别检查首层、中层、末层，总计 18 张 PNG，与从原始体素计算的窗宽窗位、方向结果逐像素比对；全部通过。六张中层输出图保存在同一验证目录。

本地预览另导入两份明确标注的测试档案：`Slicer 公开样本 · CT-chest` 和 `Slicer 公开样本 · MR-head`，来源记录随档案保存。CT 档案中另有“多器官关联演示（软件测试）”，仅验证分类关联，不描述样本真实病症。

复现：

```powershell
backend/.venv/Scripts/python.exe scripts/real-imaging-samples.py
backend/.venv/Scripts/python.exe scripts/verify-real-imaging.py
```

样本体积留在 `.cache`，没有提交大体积医学影像到 Git。

## 验证结果与边界

- 后端：原有 43 项测试在 SQLite 和独立 PostgreSQL 上通过；增加完整体积接口的数据、权限和归档拒绝检查后，SQLite 共 44 项通过。
- 数据库：迁移升级至 0003、Alembic 一致性检查、回退到 base 后再次升级全部通过；临时验证数据库已移除。
- 前端：TypeScript 检查和 Vite 生产构建通过，独立 Worker 正常打包；Mac 模态识别工具 8 项检查通过。本地渲染测试覆盖 C/Fortran 存储顺序、Vue 响应式数据跨线程传递、截断检测、最新帧调度和退出释放，并确认真实 CT/MRI 的 18 张 PNG 像素完全一致。
- 浏览器：实际操作患者录入/归档、资料保存、公开 CT/MRI 浏览和切层、确认保存，以及多器官病历保存和分类入口。
- Ruff 检查和格式化检查通过。依赖仍有弃用提示；前端主包有体积提示。

本次验证覆盖影像读取与显示，没有执行真实 GPU 权重推理，也没有连接外部 AI 服务。AI 悬浮界面为可接通现有单轮问答接口的外壳，尚不提供自主操作或多轮上下文推理。MRI 支持存储和浏览，现有 NVIDIA CT 模型不用于 MRI。DICOM 工具的合成夹具测试不等于真实 DICOM 序列或压缩传输语法验证。Docker 镜像本次未实际构建运行。
